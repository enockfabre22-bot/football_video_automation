# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Automation engine that renders short videos (football simulations/battles with club crests and MIDI piano "falling notes" animations) and publishes them to TikTok / YouTube accounts on a schedule. Code, comments, logs and commit messages are in French. Production runs on an Ubuntu VPS as a systemd daemon; development happens on Windows.

## Commands

There is no build step, linter or test suite. The modules in `app/` import each other by bare name (`from main import ...`), so run them as scripts from the repo root (paths like `output/temporary` are also resolved relative to the CWD):

```bash
python app/main.py <account_name>        # prepare AND immediately publish all slots for one account (direct/test mode)
python app/scheduler.py --daemon         # production daemon: schedules all enabled accounts (what systemd runs)
python app/scheduler.py                  # dry check: random-time draw + list detected accounts
python app/match_manager.py              # list tomorrow's matches that have both team logos
python test_accounts.py                  # list enabled accounts and their slot ids
python scripts/match_planner.py          # Tkinter GUI to edit data/matches.json (run locally, then git push)
python engines/piano/local_test.py --midi "assets/library/pop/X.mid"  # piano engine test without Docker -> output/tests/
python engines/football/local_test.py --format royale|rings|colorwar|marble|knockout|duel [--pack laliga --count 16 --seed N]
                                         # football engine test without Docker; --frames 0,300,900 = PNG preview only (fast)
python app/football_data.py              # football registry/packs self-check (missing logos, unknown keys)
python app/football_fixtures.py --all    # fetch fixtures from football-data.org, list big matches kept / skipped
python scripts/fetch_football_sounds.py  # rebuild assets/sounds/football/ from Freesound (CC0) — already committed
python scripts/midi_library.py stats|list|import|disable|enable|check  # MIDI library (assets/library)
python get_youtube_token.py              # OAuth flow -> token.json (move it to accounts/<yt_account>/token.json)
python ai_studio/cli.py create <anim> --mock  # AI studio: one full creation with a fake Claude (needs Docker image)
python ai_studio/cli.py daemon           # AI studio service (what scripts/ai-studio.service runs)
```

Set `"dry_run": true` in `config/app.json` to run the full pipeline without uploading. Note it is currently `false`.

External requirements: `ffmpeg` on PATH, `fluidsynth` + the Salamander SF2 for the piano engine (`scripts/setup_piano.sh`), Docker for sandbox steps, Processing 4 (`processing-java`, or on Windows `PROCESSING_DIR` in `.env` pointing at the Processing install so the engine calls its bundled JDK + `processing.mode.java.Commander` directly). On a headless Linux box the engine wraps Processing in `xvfb-run`. 

VPS deployment notes are in `scripts/setup_vps.sh` and `scripts/football-automation.service` (deploy = `git pull` on the VPS + `sudo systemctl restart football-automation`).

## Architecture

### Three layers, all config-driven
- **`accounts/<account_name>/config.json`** — one folder per publishing account. `platform` (`tiktok`/`youtube`), `enabled`, `metadata_rules` (how many hashtags / YouTube tags to sample), and `schedule_slots`: each slot has an `id`, a publish `window`, and an `animation_strategy` (`fixed` + `target_animation`, or `random` + optional `exclude_animations`). The folder name is the account id used everywhere. TikTok credentials come from `.env` as `<env_prefix>_CLIENT_KEY/_CLIENT_SECRET/_ACCESS_TOKEN/_REFRESH_TOKEN`; YouTube uses `accounts/<name>/token.json` (gitignored).
- **`animations/<folder>/config.json`** — self-contained render pipelines. An animation is eligible for an account only if `enabled` and the account is listed in its `accounts` array. `target_animation` must match the config's `name` field, **not** the folder name (e.g. folder `foot_ballclash` has `name: "BallClash"`). `steps` is an ordered list of `processing` (sketch folder) or `python` (script) steps. `metadata` holds pools of titles/descriptions/hashtags/youtube_tags with `{home}`, `{away}`, `{midi}` placeholders (plus the football ones, see the football engine; extra placeholders are also applied to hashtags/tags, and empty hashtags are dropped). `inputs` drives resource selection (see below).
- **`platforms/`** — upload clients (`tiktok/client.py` + `uploader.py`, `youtube/uploader.py`), dispatched by `PublicationManager.publish_video` based on the account's `platform`.

### Pipeline (`app/main.py`)
1. **Phase 1 `prepare_daily_videos(account)`** — for each slot: select animation → if `requires_match_data`, consume the next match from `data/matches.json` dated **tomorrow** whose team logos exist in `assets/logos/<Team>.png` (matches without logos are silently skipped); otherwise pick assets based on `inputs` (`library` → a song from the MIDI library via `midi_library.choose_song`, `jpg`/`jpg_portrait` → random `assets/jpg[_portrait]/*.jpg`). Then create/resume a job, generate metadata, render, and mark the job `SCHEDULED`.
2. **Phase 2 `publish_scheduled_job(job, account)`** — upload, move job to completed/failed, then always delete the final video and `output/temporary/<job_id>/` (disk space on the VPS is tight).

The **scheduler** (`app/scheduler.py`) runs Phase 1 per account once a day at *(earliest slot start − 300 min)*, then registers a one-shot `schedule` job at a random minute inside each slot's window to run Phase 2. The chosen time is persisted in the job (`metadata.planned_publish_at`); on daemon start `restore_scheduled_jobs()` reloads `SCHEDULED` jobs from `jobs/pending/` and reschedules them, publishes them immediately if their window ended less than `CATCH_UP_MAX_HOURS` ago, or discards them (`main.discard_job`) — so restarting the service no longer loses the day's publications. Disk hygiene (`app/maintenance.py`): `cleanup_disk()` runs at daemon start and before each daily prep — it discards unfinished (`PENDING`/`RUNNING`) jobs dated today or earlier, wipes partial frames of other unfinished jobs, and deletes `output/temporary/*` and `output/videos/*` entries not belonging to a pending job (except manual renders `test_*` / `manual_*` younger than 12 h, so restarting the service during a `test_animation.py` / `publish_now.py` render does not wipe it). `has_enough_disk_space()` refuses a render below `min_free_disk_gb` (animation config, else `config/app.json`). A full disk once crashed the whole daemon (Processing PNG frames can reach tens of GB per long video).

### Animation contract (engine ↔ steps)
`AnimationManager.execute_animation` writes `output/temporary/<job_id>/job.json` (job_id, match, metadata, `resources` with absolute asset paths, `work_dir`, `output_video`) and runs every step with that path as the sole argument (`python script.py <job.json>` / `processing-java --sketch=... --run <job.json>`; Processing sketches read it via `args[0]`). Sketches render frames into `<work_dir>/frames/` and call `exit()`; the final Python step muxes frames + audio with ffmpeg into `output_video` (`output/videos/<job_id>.mp4`). A step fails on non-zero exit code; the job fails if `output_video` is missing or empty. A sketch may also drop `<work_dir>/thumbnail_source.jpg`, which is picked up as the upload thumbnail; alternatively `thumbnail.enabled` in the animation config renders one via `app/thumbnail_generator.py`.

### Football engine (`engines/football/`) — 6 formats for `youtube_avantfoot` + `tiktok_main` (English content)
Replaced the old Processing animations `animation_01` / `BallClash` (now `enabled: false`; their Shorts plateaued at ~1-2k views, ~55-65% watched). One raylib binary (`scene/`, sandbox profile `raylib_box2d`, no Box2D: own deterministic physics in `fb_common.h`), one animation folder per format, all with steps `prepare.py --format X` (python) → `scene/` (sandbox, `video_from: football/video.json`, `sounds_dir: ../../assets/sounds/football`) → `finalize.py` (stadium ambience bed from `assets/sounds/football/beds/` with crowd swells on big events of `sandbox_out/events.jsonl`, loudnorm −14 LUFS, thumbnail at `metrics.json` `scene.thumb_time`).
- **Formats** (`scene.txt format=`, `create_scene()` in `fb_main.cpp`): `fb_royale` (Last Club Standing: N crests, HP, shrinking arena, heart pickups), `fb_rings` (Escape the Rings: 4 rotating neon rings with a gap, first crossing shatters a ring), `fb_colorwar` (Pong-Wars-style territory grid + paint bombs, 26 s countdown), `fb_marble` (vertical marble race on a procedurally stacked course, camera follows the leader, fast-forward after the podium, full predicted table with CL/relegation zones for full leagues), `fb_knockout` (8-team bracket, duels with lives in a bottom arena, sudden-death final), `fb_duel` (Big Match Duel: the 2 teams of a real match on a mini pitch, HP + football power-ups: boots, glove shield, red card freeze, heart).
- **Drama selection**: every scene splits a pure deterministic `XxxSim` (fixed `SIM_DT` = 1/240 s, own `Rng`, events) from its presentation. `setup()` simulates `candidates` (40, marble 24) seeds derived from `ctx.seed`, scores each (`score()`: duration, early first event, regular pacing, lead changes, close finish) and replays the best one live. Pacing regulators inside the sims keep durations stable whatever the team count (royale: damage multiplier vs a target elimination timeline + hidden per-team armor; duel: HP vs a target curve; rings: the current ring's gap widens after a target interval). The known decisive moment is played in slow motion (`desired_time_scale()`); `ctx.finish()` ends the video after the outro (winner card / table). Videos last ~24-33 s. `FB_DEBUG=1` prints the chosen scenario's timeline.
- **Shared look** (`fb_common.h`): 1080x1920 design space (`Gfx::S` = render width / 1080, so 1440p/4K is just `--width/--height` in prepare), SDF anti-aliased shapes (`Gfx::shape` modes: disc, ring, arc with round caps, rounded rect...), quarter-res bloom, Anton/Poppins fonts loaded at render size, `draw_token()` (club ring + light disc + crest + specular), `Fx` particles (confetti, sparks, glass shards, splashes, shockwaves, floating texts), `header()` (chip + 2-line title), `draw_toasts()`, `winner_card()` (crown, rays, name, CTA "COMMENT YOUR ...").
- **Teams** (`app/football_data.py`): `data/teams.json` = registry keyed by logo file name (`assets/logos/<key>.png`): English display name, short code, identity colours (pre-brightened for dark backgrounds), hashtag. `data/football_packs.json` = groups (5 leagues — current line-ups, refreshed weekly from the API into `data/football_packs_live.json` (gitignored) which `football_data.packs()` overlays —, Champions League, Top European, Big 6, World Cup / Euro / AFCON / Copa América nations), teams ordered by popularity (`popular_bias` favours the top). N-team animations declare `"inputs": ["football_pack"]` + a `football` section (`packs`, `team_counts`, `popular_bias`, `repeat_days`, `prefer_full_pack`); `main.py` draws the line-up (avoiding packs used recently on the account: `data/football_history.json`, gitignored VPS state), stores it in `resources.football_lineup` and fills `{competition} {competition_tag} {count} {noun} {Noun} {single}` in titles/descriptions/hashtags/tags. Matches (`fb_duel`) get English names, `home_tag`/`away_tag` (#PSG) and `{competition}` from the registry via `match_manager.py` (team names typed in any case/language resolve through `football_data.resolve_key`). `"big_match": true` in `data/matches.json` (checkbox in `match_planner.py`) puts a match first.
- **Automatic fixtures** (`app/football_fixtures.py`, key `FOOTBALL_DATA_TOKEN` in `.env`, football-data.org free tier: 12 competitions, 10 req/min): `sync()` runs at the start of every `prepare_daily_videos` (cached 3 h), fetches the next 3 days for PL/PD/SA/BL1/FL1/CL/PPL/WC/EC, maps API teams to registry keys (`data/team_aliases.json` by API id, then name/shortName/token/TLA matching; teams without logo are skipped and logged), keeps only big matches (`big_match_score`: derby list, both teams in the top 7 of their league pack, or a "Top European" giant in the CL) and writes `data/matches_api.json` (gitignored) with the local kickoff. `python app/football_fixtures.py --all` shows what is kept/skipped. **The duel now uses TODAY's matches** (manual `data/matches.json` first, then API by score), unlike the old animations which used tomorrow's.
- **Slots**: both accounts have `<prefix>_matin`, `_fin_matinee`, `_soir` (random among the 5 N-team formats, `exclude_animations: ["fb_duel"]`; an animation is not drawn twice in the same day's preparation while others remain) and `_match_du_jour` (`fixed` `fb_duel`, `"max_matches": 2` → expanded by `main.expand_match_slots` into `_match_du_jour` + `_match_du_jour_2`, `"publish_before_kickoff_min": 180`). `main.kickoff_window()` turns the kickoff into a ±10 min publish window (2nd duel with the same kickoff 40 min earlier; late preparation → as soon as possible if ≥45 min remain, else the match is dropped) and stores `metadata.publish_deadline` = kickoff; the scheduler publishes a late duel immediately instead of the next day and discards it once the match has started (also on restore). When an animation needs a match and none is left, `main.py` draws another animation (the extra `_2` slot is just skipped: `"skip_without_match": true`).
- **Sounds**: `assets/sounds/football/` (76 files, CC0 from Freesound, provenance in `SOURCES.md`, rebuilt by `scripts/fetch_football_sounds.py`): variants `name_1..k` (pitch-shifted) to avoid repetition; scenes call `FootballScene::sound(ctx, base, variants, vol)`. Use `FB_GOLD` (not raylib's `GOLD` macro).

### Long-form quiz "Guess the Football Player" (`quiz_guess_player`, 16:9, `youtube_avantfoot`)
Same engine/binary as the Shorts (`format=quiz` → `fb_main.cpp` switches the design space to 1920x1080: `DW`/`DH` are `inline` globals in `fb_common.h`, never assume 1080x1920 in shared code). ~8-9 min at 30 fps, ≥ 8 min for mid-roll ads.
- **Data** (`scripts/quiz_build_players.py`, run on the PC — rembg is not installed on the VPS — then commit `data/quiz/players_db.json` + `assets/quiz/`): curated list `data/quiz/players.json` (name/search/qid + difficulty 1-4) → Wikidata (CC0): club career P54 with dates (national/youth/reserve teams filtered by P31 + `RESERVE_WORDS`, undated stints kept in claim order), sport nationality P1532 → ISO flag (flagcdn, public domain), position P413, birth P569; photo P18 from Wikimedia Commons **only with a free licence** (CC0/CC BY/CC BY-SA/PD, author + licence stored for the mandatory credit), background removed with rembg `u2net_human_seg` → `assets/quiz/players/<QID>.png`; free Commons crest (P154) for clubs missing from `assets/logos` → `assets/quiz/crests/`, else initials. Wikimedia throttles automated image downloads hard (429 + Retry-After 120 s): keep ≥ 2.5 s between images; raw API answers are cached in `data/quiz/cache/` (gitignored). `--only NAME`, `--all` (recompute careers from cache), `--refresh`. Wikidata has errors: **`data/quiz/overrides.json`** (exclude / difficulty / name / remove_clubs / full career) is applied by `quiz_prepare.py`; clubs are re-matched to the registry at prep time (`resolve_club`, aliases by Wikidata id in `data/team_aliases.json` → `wikidata`).
- **Prep** (`engines/football/quiz_prepare.py`): picks ≥ 7 players per level (EASY/MEDIUM/HARD/IMPOSSIBLE) with a photo, avoiding the last 6 quizzes (`data/quiz_history.json`, gitignored VPS state), adds players until `--min-seconds` (495); computes the whole timeline (constants at the top: clue times, `CLUB_STEP`, `COUNTDOWN` 5 s, `REVEAL`) into `football/quiz.txt` (`T`/`L`/`R`/`C` lines) — the scene follows it literally; writes silhouette masks (`<QID>_mask.png`), `teams.txt` (clubs), YouTube chapters + title + description with photo credits into `<work_dir>/metadata_override.json`. No apps/goals on screen (Wikidata stats are unreliable): reveal shows birth year + number of clubs.
- **Scene** (`quiz_scene.cpp`): intro with glowing silhouettes, level cards, rounds (flag, position chip, career crests popping in order with years, silhouette = black mask drawn in the HUD pass AFTER the bloom so only the outline glows, 5 s countdown with clock, reveal = colour photo crossfade + name + club names), outro with score tiers + "COMMENT YOUR SCORE".
- **Finalize**: `finalize.py --no-bed --music-dir assets/music/quiz --quiz-thumbnail`: Kevin MacLeod tracks (CC BY 4.0, `credits.json`) chained with 3 s crossfades, credit appended to `metadata_override.json`; custom 1280x720 thumbnail (`quiz_thumbnail.py`). `AnimationManager.execute_animation` (and `publish_now.py`) merge `metadata_override.json` into the job metadata after a successful render (`apply_metadata_override`) — any animation can write its own title/description this way.
- **Scheduling**: `"exclude_from_random": true` keeps it out of random slots; slot `avantfoot_quiz_dimanche` (`"days": ["sun"]`, 16:00-16:30). Manual: `python scripts/publish_now.py youtube_avantfoot --animation quiz_guess_player`. Local test: `python engines/football/local_test.py --format quiz [--max-rounds 8]`.

### Piano engine (`engines/piano/`) — 3 looks, drawn at random per slot
Nine piano animations share one engine; configs differ only by step `args` (`--format portrait|landscape`, `--max-seconds`, `--excerpt auto|full`, `--names artist_title|title_artist`, `--style falling|premium|neon|liquid`). Steps: `prepare.py` (python) → `scene/` (sandbox, `video_from: piano/video.json` = duration computed from the MIDI) → `finalize.py --thumbnail` (mux + thumbnail).
- **MIDI library** (`assets/library/`, `app/midi_library.py`, CLI `scripts/midi_library.py`): ~675 curated songs in `<category>/<Artist - Title[ - EASY]>.mid` (categories pop, film, anime, game, tv, classical, modern_piano, holiday) + `library.json` (title, artist, category, popularity 1–3, easy, duration, enabled, source). Piano animations use `"inputs": ["library", ...]` and an optional `"library": {"categories", "min_duration", "category_weights", "repeat_days"}` section. `choose_song` filters (enabled, categories, min duration, holiday only 15 Nov–6 Jan), excludes songs used on the account within `repeat_days` (`data/song_history.json`, gitignored VPS state, written by `remember` at prep time), draws a category by weight then a song weighted by popularity (3→×9, 2→×4, 1→×1). Add songs with `python scripts/midi_library.py import <file|dir> --category film --popularity 3` (rejects < 35 s, < 120 notes, drums/non-piano). Classical entries from piano-midi.de (CC BY-SA, Bernd Krueger) were renamed by hand from their cryptic file names; the old `assets/midi` / `assets/midi2` folders were removed (git history).
- **SEO / metadata** (`app/song_meta.py`): `main.py` parses the MIDI filename into `{title}`, `{artist}`, `{artist_tag}` (hashtag-safe), `{easy}` ("Easy " for `- EASY` files) and `{midi}` (= "Title - Artist"; midi2 = "Artist - Title", midi = "Title - Composer"; "(2)" and "Piano Edition" dropped), then fills titles/descriptions/hashtags/tags (`fill`, `fill_list` tidy leftovers when a field is empty). `generate_job_metadata` always keeps the pool entries containing a placeholder and samples generic ones for the rest of the quota; on YouTube accounts hashtags are NOT appended to the title (the uploader puts them in the description). `youtube_piano` has `category_id: "10"` (Music — the uploader default 17 = Sports is for the football channels) and `default_language: "en"`; the uploader keeps tags within YouTube's 500-character budget (song-specific tags first). Songs whose catalogue `source` is piano-midi.de get the mandatory CC BY-SA credit appended to the description.
- **Slots use `animation_strategy: random`**: `youtube_piano` Shorts slots draw among `midi_falling_short`, `neon_piano_short`, `liquid_piano_short` (`exclude_animations` = the 16:9 ones), its `video_01_soir` slot among `midi_falling_ytb`, `neon_piano`, `liquid_piano` (excludes the Shorts); `tiktok_ItPiano` draws among `midi_falling_tkt`, `neon_piano_tkt`, `liquid_piano_tkt`. Keep these exclusion lists in sync when adding a piano animation.
- `prepare.py` reads the MIDI (`piano_midi.py`: tempo map, hands from tracks or pitch, bars/beats), picks the excerpt (`choose_excerpt`: most repeated + intense passage = chorus, first occurrence, starts on a bar; the first note hits at `--lead` = 0.12 s), recreates dynamics when velocities are flat (`humanize_velocities`) and adds a harmony-following sustain pedal when the file has none (`auto_pedal`), renders audio with FluidSynth + `assets/soundfonts/` Salamander Grand Piano SF2 (gitignored, `bash scripts/setup_piano.sh`) then convolution reverb + loudnorm −14 LUFS (`piano_audio.py`), picks a random palette per video (`PALETTES` / `PREMIUM_PALETTES` / `NEON_PALETTES`, seeded by job_id), and writes `<work_dir>/piano/{scene.txt, notes.txt (video-time), background.png, title.png, font.ttf, audio.wav, video.json, meta.json}` (Poppins fonts in `assets/fonts/`).
- `scene/` (raylib, reads `$PIANO_DIR` or `/work/piano`) is ONE binary; `create_scene()` in `piano_scene.cpp` picks the style from `scene.txt style=`. Shared pieces in `piano_common.h`: SDF-shader anti-aliased shapes (`SHAPE_FS` styles 0/1/2 falling, 5 premium glass notes, 9 neon notes, 10 played key, 11/12 flat 2D keys), quarter-res bloom built in `render_offscreen()` (optional Scene hook of the runtime, called before `draw()`; `Gfx::spreads` adds blur passes), `Keyboard`, `NoteTrack`, sparks, dust. No sound events: `finalize.py` muxes `audio.wav`.
  - `premium` ("Aurora Keys", `premium_scene.cpp`, used by `midi_falling_*`): glass notes with note names, harmony-driven aurora backdrop, keyboard lit from inside with key names, sober impacts.
  - `neon` (`neon_scene.cpp`, used by `neon_piano*`, modelled on reference Shorts sent by the user): black starfield, SOLID neon notes with the note name (sharps/flats from `detect_key_fifths` → `key_fifths`), strong bloom, FLAT 2D keyboard with a FIXED view (the user rejected 3D lips/floating black keys, a panning camera, floor reflections of notes and a "Ped." marker), played keys fully coloured, dust fountains (`Mote`s) from struck/held keys.
  - `liquid` (`liquid_scene.cpp`, used by `liquid_piano*`, modelled on reference Shorts sent by the user): pure black background, rounded bars filled with an animated LIQUID light texture (SHAPE_FS style 13: fbm veins attached to the note via the `scroll` uniform = t × pps × `render_scale`, set with `Gfx::set_liquid` before `begin_shape(13)`), note names at the bottom of notes, FULL 88-key keyboard (A0–C8, fixed, letters under every white key), glowing hit line in the theme colour (`line_color` from `LIQUID_PALETTES`, which hold (right, left, line) triples), smoke/flame wisps stretched along their motion, song title centred in serif (`assets/fonts/LibreBaskerville-Regular.ttf`, OFL) and "Beginner/Intermediate/Advanced Piano Tutorial" under the keyboard (prepare: EASY file or < 3.5 notes/s = Beginner, < 7 = Intermediate).
  - `falling` (`piano_scene.cpp`): the original simple style, default of `prepare.py`, not used by any animation.
- Abandoned experiments (bounce, reveal, highway, eclipse, aurora) were deleted; see git history if needed.
- Local test without Docker (Windows w64devkit raylib at `C:/raylib`, or Linux raylib): `python engines/piano/local_test.py --midi "assets/library/pop/X.mid" --style neon [--format landscape --excerpt full] [--scale 2 = 4K]` → `output/tests/piano_<ts>/`. fluidsynth must be on PATH (or `FLUIDSYNTH_PATH`); `PIANO_SOUNDFONT` overrides the SF2.

### Job state machine (`app/job_manager.py`)
Jobs are JSON files: `jobs/pending/` (`PENDING` → `RUNNING` → `VIDEO_READY` → `SCHEDULED`) then moved to `jobs/completed/` (`PUBLISHED`) or `jobs/failed/` (`FAILED`). `job_id = <date>_<home>_<away>_<animation_name>_<account>` (spaces → `_`; jobs created before 2026-11-23 have no `_<account>` suffix — lookups go by the `<date>_<home>_<away>_` prefix + the `account` field, so both formats work). For non-match animations `home` is the slot id and `away` is `no_match`; keep slot ids unique across accounts anyway (they are prefixed: `avantfoot_*`, `tkmain_*`...). Idempotence: a job already `PUBLISHED` for the same date/home/away/account is skipped; an existing pending job is resumed without re-rendering if its video still exists, and keeps its own animation and football line-up (`match.resources.football_lineup`) even if the slot would now draw another one.

### Sandbox steps (Docker) — Raylib + Box2D
Step `"type": "sandbox"` (handled by `app/sandbox_runner.py`) compiles and runs a program inside Docker with no network, read-only rootfs, no host env vars, CPU/RAM/pids/time limits (from `config/ai.json` → `sandbox`) and the host UID. Mounts: the animation's `source` dir → `/src:ro`, the profile runtime → `/runtime:ro`, `sounds_dir` → `/sounds:ro`, the job work dir → `/work` (only writable mount). Profiles live in `sandbox/profiles/<name>/` (`profile.json` with image + build/run commands, `Dockerfile`, `runtime/`). Build the image on the VPS with `bash scripts/build_sandbox.sh raylib_box2d` (raylib 5.5 + Box2D 2.4.2 C++ API — same API as the channel brief examples; `<Box2D/Box2D.h>` compat header provided; Mesa software GL under Xvfb, ffmpeg).

`raylib_box2d` contract (`runtime/anim_runtime.h`): a scene implements `init/update(dt)/draw` + `create_scene()`; it draws in logical coordinates (the runtime scales to the render size), advances with a fixed `dt = 1/fps` (never `GetFrameTime()`), uses `ctx.randf/randi` (seeded), and calls `ctx.sound(name, volume)` — the runtime mixes those events from `sounds_dir` into the video (no separate audio script needed). The runtime reads `/work/sandbox_job.txt` (key=value written by the runner), pipes raw RGBA frames to ffmpeg (no PNGs on disk), and writes `sandbox_out/{video.mp4, events.jsonl, metrics.json}`; `mode=preview` only draws and exports the requested `capture_frames` (reduced size, PNG) while simulating every frame (for the AI studio); `draw()` must therefore never modify state. Example: `animations/raylib_demo_balls/` (assigned to no account). Test any animation without publishing: `python scripts/test_animation.py <name>` → `output/tests/`.

### AI animations
An animation whose config has `"type": "ai"` is never rendered by the scheduler: the scheduler only consumes the stock in `ai_data/<animation>/creations/<id>/` (`state.json` + `final.mp4` + `thumbnail.jpg`, gitignored, lives on the VPS) via `app/ai_stock.py`. `resolve_ai_animation()` in `main.py` checks the stock; if empty it switches to the slot's `fallback_animation` (or re-draws for `random` slots, or skips). On job creation a servable `READY` creation is reserved (`RESERVED`) — themed creations (`publish_after`/`publish_before`, e.g. Christmas) only inside their window and first, outdated ones become `EXPIRED` (video deleted) — `_deliver_ai_creation` **copies** its video, and the creation's own `metadata` (title/description/hashtags/youtube_tags written by the studio) overrides the animation's pools; `publish_overrides` (e.g. YouTube private) is merged over the account config in `PublicationManager.publish_video`. After publishing: success → `PUBLISHED` + line in `ai_data/<anim>/history/publications.jsonl` + stock video deleted; failure → back to `READY`.

**AI studio** (`ai_studio/`, separate process, run from repo root; modules import each other by bare name and add `app/` to `sys.path` via `studio_common.py`): `python ai_studio/cli.py status|daemon [--mock] [--once]|create <anim> [--mock] [--event NAME|--no-event] [--design-only]|resume <id>|render <id>|discard <id>|history <channel>|costs|events <channel>|context <anim>` (`resume` also reopens a FAILED creation at its failed step; `render` = human override: final render despite a rejected review). `--mock` uses `MockClaude` (no API, returns `ai_studio/mock/scene.cpp`); without it `config/ai.json` must have `enabled: true` and `.env` must contain `ANTHROPIC_API_KEY` (never passed to Docker). Pipeline (`pipeline.py`, every step persisted in `state.json`, resumable): `concept` (Sonnet, structured JSON) → local anti-repetition (`similarity.py`, vs channel cards) → `code` → `preview` (Docker build + low-res full simulation, `checks.py` auto-checks from `metrics.json` + frames; failures → `fix` patches `{file, old, new}`, max `max_code_fixes`, stop when the same error repeats) → `review` (Sonnet on 8 preview frames) → `render` (runs the animation's `steps`: `ai_generated` = final Docker render, then e.g. `scripts/steps/add_background_music.py`) → `finalize` (ffprobe check, most colorful/contrasted of 12 frames as thumbnail, Haiku writes title/description/tags + history card) → `READY`. **Production = `daemon.py`** (systemd `scripts/ai-studio.service`, separate from the scheduler): every `studio.loop_interval_minutes` it resumes interrupted creations, runs a **design session** when the stock is short (`stock_target()` = `ai.stock_days` × slots per day of the accounts using the animation; batch of `studio.design_batch_size` creations in a row so they share the Claude cache, capped by `max_creations_per_day`, stops after 2 failures in a row) where each creation stops at `CODE_READY` (code validated, `run(stop_before_render=True)`), then a **render queue** renders one `CODE_READY` creation at a time (no API except the Haiku card). `CODE_READY` cards count for anti-repetition. Visual review is optional (`limits.review_enabled`); a score ≤ `review_rewrite_score` triggers one full code rewrite (`max_code_rewrites`) fed with the reviewer's issues instead of patches. Creativity: each concept gets random inspiration axes (`inspiration.py`: physics family, palette, composition, stake = what keeps viewers to the end; overridable per channel with `ai_channels/<channel>/inspiration.json`), avoiding recently used ones; duration is free within `ai.video.duration_range_s` (concept field `duration_s`), and a scene may end the video itself with `ctx.finish()` (runtime stops, `metrics.json` reports `duration`/`ended_by_scene`; the preview re-times the duration once and the final check uses `effective_duration_s`). Only one studio process at a time (`studio_lock()` on `ai_data/.studio.lock`): stop the service before manual `create/resume/render`. Mock creations (`state.mock`) are never served by the stock nor counted by the real daemon. Every call goes through `claude_client.py`: stable prefix (profile `contract.md` + runtime headers + `ai_channels/<channel>/brief/` brief, examples, images) cached 1 h, budgets checked before each call (`ledger.py`, `ai_data/usage.jsonl`). The output schema and `effort` are part of the cached prefix, so all Sonnet tasks share ONE schema (`prompts.SONNET_SCHEMA`, one nullable field per task) and the same effort — a per-task schema rewrote the ~95k-token cache on every task. Mid-stream disconnects are retried in `claude_client.py` (`api_stream_attempts`). Channel layout: `ai_channels/<channel>/brief/{brief.md,examples/,images/}` + optional `events.json`; creative history shared by the channel's animations in `ai_data/channels/<channel>/creative/`. Settings: global in `config/ai.json` (models, effort/max_tokens per task, prices, budgets, limits, sandbox), per animation in its `ai` section (`channel`, `profile`, `video`, `max_bodies`, `sound`, `stock_target`, `events`, `publish_overrides`). `app/render_lock.py` is a cross-process lock: the scheduler takes it non-blocking, the studio blocking. AI scenes must call `anim_watch_world()` (`runtime/anim_box2d.h`): the runtime then reports bodies / off-screen / lost / NaN / moving fraction per tenth of the video in `metrics.json`, used to reject broken or frozen simulations.

### Logging
`setup_logging()` replaces `sys.stdout` with a tee that timestamps every `print()` into `logs/automation.log`. Use `print` for logging; there is no `logging` module setup.
