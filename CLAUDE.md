# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Automation engine that renders short videos (football match "simulations" and MIDI piano "falling notes" animations) and publishes them to TikTok / YouTube accounts on a schedule. Code, comments, logs and commit messages are in French. Production runs on an Ubuntu VPS as a systemd daemon; development happens on Windows.

## Commands

There is no build step, linter or test suite. The modules in `app/` import each other by bare name (`from main import ...`), so run them as scripts from the repo root (paths like `output/temporary` are also resolved relative to the CWD):

```bash
python app/main.py <account_name>        # prepare AND immediately publish all slots for one account (direct/test mode)
python app/scheduler.py --daemon         # production daemon: schedules all enabled accounts (what systemd runs)
python app/scheduler.py                  # dry check: random-time draw + list detected accounts
python app/match_manager.py              # list tomorrow's matches that have both team logos
python test_accounts.py                  # list enabled accounts and their slot ids
python scripts/match_planner.py          # Tkinter GUI to edit data/matches.json (run locally, then git push)
python get_youtube_token.py              # OAuth flow -> token.json (move it to accounts/<yt_account>/token.json)
python ai_studio/cli.py create <anim> --mock  # AI studio: one full creation with a fake Claude (needs Docker image)
python ai_studio/cli.py daemon           # AI studio service (what scripts/ai-studio.service runs)
```

Set `"dry_run": true` in `config/app.json` to run the full pipeline without uploading. Note it is currently `false`.

External requirements: `ffmpeg` on PATH, Processing 4 (`processing-java`, or on Windows `PROCESSING_DIR` in `.env` pointing at the Processing install so the engine calls its bundled JDK + `processing.mode.java.Commander` directly). On a headless Linux box the engine wraps Processing in `xvfb-run`. 

VPS deployment notes are in `scripts/setup_vps.sh` and `scripts/football-automation.service` (deploy = `git pull` on the VPS + `sudo systemctl restart football-automation`).

## Architecture

### Three layers, all config-driven
- **`accounts/<account_name>/config.json`** — one folder per publishing account. `platform` (`tiktok`/`youtube`), `enabled`, `metadata_rules` (how many hashtags / YouTube tags to sample), and `schedule_slots`: each slot has an `id`, a publish `window`, and an `animation_strategy` (`fixed` + `target_animation`, or `random` + optional `exclude_animations`). The folder name is the account id used everywhere. TikTok credentials come from `.env` as `<env_prefix>_CLIENT_KEY/_CLIENT_SECRET/_ACCESS_TOKEN/_REFRESH_TOKEN`; YouTube uses `accounts/<name>/token.json` (gitignored).
- **`animations/<folder>/config.json`** — self-contained render pipelines. An animation is eligible for an account only if `enabled` and the account is listed in its `accounts` array. `target_animation` must match the config's `name` field, **not** the folder name (e.g. folder `foot_ballclash` has `name: "BallClash"`). `steps` is an ordered list of `processing` (sketch folder) or `python` (script) steps. `metadata` holds pools of titles/descriptions/hashtags/youtube_tags with `{home}`, `{away}`, `{midi}` placeholders. `inputs` drives resource selection (see below).
- **`platforms/`** — upload clients (`tiktok/client.py` + `uploader.py`, `youtube/uploader.py`), dispatched by `PublicationManager.publish_video` based on the account's `platform`.

### Pipeline (`app/main.py`)
1. **Phase 1 `prepare_daily_videos(account)`** — for each slot: select animation → if `requires_match_data`, consume the next match from `data/matches.json` dated **tomorrow** whose team logos exist in `assets/logos/<Team>.png` (matches without logos are silently skipped); otherwise pick random assets based on `inputs` (`midi`/`midi2` → `assets/midi[2]/*.mid`, `jpg`/`jpg_portrait` → `assets/jpg[_portrait]/*.jpg`; the song title/author is parsed from the MIDI filename `Author - Title`). Then create/resume a job, generate metadata, render, and mark the job `SCHEDULED`.
2. **Phase 2 `publish_scheduled_job(job, account)`** — upload, move job to completed/failed, then always delete the final video and `output/temporary/<job_id>/` (disk space on the VPS is tight).

The **scheduler** (`app/scheduler.py`) runs Phase 1 per account once a day at *(earliest slot start − 300 min)*, then registers a one-shot `schedule` job at a random minute inside each slot's window to run Phase 2. The chosen time is persisted in the job (`metadata.planned_publish_at`); on daemon start `restore_scheduled_jobs()` reloads `SCHEDULED` jobs from `jobs/pending/` and reschedules them, publishes them immediately if their window ended less than `CATCH_UP_MAX_HOURS` ago, or discards them (`main.discard_job`) — so restarting the service no longer loses the day's publications. Disk hygiene (`app/maintenance.py`): `cleanup_disk()` runs at daemon start and before each daily prep — it discards unfinished (`PENDING`/`RUNNING`) jobs dated today or earlier, wipes partial frames of other unfinished jobs, and deletes `output/temporary/*` and `output/videos/*` entries not belonging to a pending job. `has_enough_disk_space()` refuses a render below `min_free_disk_gb` (animation config, else `config/app.json`). A full disk once crashed the whole daemon (Processing PNG frames can reach tens of GB per long video).

### Animation contract (engine ↔ steps)
`AnimationManager.execute_animation` writes `output/temporary/<job_id>/job.json` (job_id, match, metadata, `resources` with absolute asset paths, `work_dir`, `output_video`) and runs every step with that path as the sole argument (`python script.py <job.json>` / `processing-java --sketch=... --run <job.json>`; Processing sketches read it via `args[0]`). Sketches render frames into `<work_dir>/frames/` and call `exit()`; the final Python step muxes frames + audio with ffmpeg into `output_video` (`output/videos/<job_id>.mp4`). A step fails on non-zero exit code; the job fails if `output_video` is missing or empty. A sketch may also drop `<work_dir>/thumbnail_source.jpg`, which is picked up as the upload thumbnail; alternatively `thumbnail.enabled` in the animation config renders one via `app/thumbnail_generator.py`.

Several animations duplicate their sketches/compilers (`midi_falling_short`, `midi_falling_tkt`, `midi_falling_ytb`); a fix in one usually needs to be applied to the others.

### Job state machine (`app/job_manager.py`)
Jobs are JSON files: `jobs/pending/` (`PENDING` → `RUNNING` → `VIDEO_READY` → `SCHEDULED`) then moved to `jobs/completed/` (`PUBLISHED`) or `jobs/failed/` (`FAILED`). `job_id = <date>_<home>_<away>_<animation_name>` (spaces → `_`). For non-match animations `home` is the slot id and `away` is `no_match`, so **slot ids must be unique across accounts**. Idempotence: a job already `PUBLISHED` for the same date/home/away/account is skipped; an existing pending job is resumed without re-rendering if its video still exists. Note the account name is not part of `job_id`, so two accounts rendering the same match with the same animation share a job filename.

### Sandbox steps (Docker) — Raylib + Box2D
Step `"type": "sandbox"` (handled by `app/sandbox_runner.py`) compiles and runs a program inside Docker with no network, read-only rootfs, no host env vars, CPU/RAM/pids/time limits (from `config/ai.json` → `sandbox`) and the host UID. Mounts: the animation's `source` dir → `/src:ro`, the profile runtime → `/runtime:ro`, `sounds_dir` → `/sounds:ro`, the job work dir → `/work` (only writable mount). Profiles live in `sandbox/profiles/<name>/` (`profile.json` with image + build/run commands, `Dockerfile`, `runtime/`). Build the image on the VPS with `bash scripts/build_sandbox.sh raylib_box2d` (raylib 5.5 + Box2D 2.4.2 C++ API — same API as the channel brief examples; `<Box2D/Box2D.h>` compat header provided; Mesa software GL under Xvfb, ffmpeg).

`raylib_box2d` contract (`runtime/anim_runtime.h`): a scene implements `init/update(dt)/draw` + `create_scene()`; it draws in logical coordinates (the runtime scales to the render size), advances with a fixed `dt = 1/fps` (never `GetFrameTime()`), uses `ctx.randf/randi` (seeded), and calls `ctx.sound(name, volume)` — the runtime mixes those events from `sounds_dir` into the video (no separate audio script needed). The runtime reads `/work/sandbox_job.txt` (key=value written by the runner), pipes raw RGBA frames to ffmpeg (no PNGs on disk), and writes `sandbox_out/{video.mp4, events.jsonl, metrics.json}`; `mode=preview` only draws and exports the requested `capture_frames` (reduced size, PNG) while simulating every frame (for the AI studio); `draw()` must therefore never modify state. Example: `animations/raylib_demo_balls/` (assigned to no account). Test any animation without publishing: `python scripts/test_animation.py <name>` → `output/tests/`.

### AI animations
An animation whose config has `"type": "ai"` is never rendered by the scheduler: the scheduler only consumes the stock in `ai_data/<animation>/creations/<id>/` (`state.json` + `final.mp4` + `thumbnail.jpg`, gitignored, lives on the VPS) via `app/ai_stock.py`. `resolve_ai_animation()` in `main.py` checks the stock; if empty it switches to the slot's `fallback_animation` (or re-draws for `random` slots, or skips). On job creation a servable `READY` creation is reserved (`RESERVED`) — themed creations (`publish_after`/`publish_before`, e.g. Christmas) only inside their window and first, outdated ones become `EXPIRED` (video deleted) — `_deliver_ai_creation` **copies** its video, and the creation's own `metadata` (title/description/hashtags/youtube_tags written by the studio) overrides the animation's pools; `publish_overrides` (e.g. YouTube private) is merged over the account config in `PublicationManager.publish_video`. After publishing: success → `PUBLISHED` + line in `ai_data/<anim>/history/publications.jsonl` + stock video deleted; failure → back to `READY`.

**AI studio** (`ai_studio/`, separate process, run from repo root; modules import each other by bare name and add `app/` to `sys.path` via `studio_common.py`): `python ai_studio/cli.py status|daemon [--mock] [--once]|create <anim> [--mock] [--event NAME|--no-event] [--design-only]|resume <id>|render <id>|discard <id>|history <channel>|costs|events <channel>|context <anim>` (`resume` also reopens a FAILED creation at its failed step; `render` = human override: final render despite a rejected review). `--mock` uses `MockClaude` (no API, returns `ai_studio/mock/scene.cpp`); without it `config/ai.json` must have `enabled: true` and `.env` must contain `ANTHROPIC_API_KEY` (never passed to Docker). Pipeline (`pipeline.py`, every step persisted in `state.json`, resumable): `concept` (Sonnet, structured JSON) → local anti-repetition (`similarity.py`, vs channel cards) → `code` → `preview` (Docker build + low-res full simulation, `checks.py` auto-checks from `metrics.json` + frames; failures → `fix` patches `{file, old, new}`, max `max_code_fixes`, stop when the same error repeats) → `review` (Sonnet on 8 preview frames) → `render` (runs the animation's `steps`: `ai_generated` = final Docker render, then e.g. `scripts/steps/add_background_music.py`) → `finalize` (ffprobe check, thumbnail, Haiku writes title/description/tags + history card) → `READY`. **Production = `daemon.py`** (systemd `scripts/ai-studio.service`, separate from the scheduler): every `studio.loop_interval_minutes` it resumes interrupted creations, runs a **design session** when the stock is short (`stock_target()` = `ai.stock_days` × slots per day of the accounts using the animation; batch of `studio.design_batch_size` creations in a row so they share the Claude cache, capped by `max_creations_per_day`, stops after 2 failures in a row) where each creation stops at `CODE_READY` (code validated, `run(stop_before_render=True)`), then a **render queue** renders one `CODE_READY` creation at a time (no API except the Haiku card). `CODE_READY` cards count for anti-repetition. Visual review is optional (`limits.review_enabled`, off by default). Only one studio process at a time (`studio_lock()` on `ai_data/.studio.lock`): stop the service before manual `create/resume/render`. Mock creations (`state.mock`) are never served by the stock nor counted by the real daemon. Every call goes through `claude_client.py`: stable prefix (profile `contract.md` + runtime headers + `ai_channels/<channel>/brief/` brief, examples, images) cached 1 h, budgets checked before each call (`ledger.py`, `ai_data/usage.jsonl`). The output schema and `effort` are part of the cached prefix, so all Sonnet tasks share ONE schema (`prompts.SONNET_SCHEMA`, one nullable field per task) and the same effort — a per-task schema rewrote the ~95k-token cache on every task. Mid-stream disconnects are retried in `claude_client.py` (`api_stream_attempts`). Channel layout: `ai_channels/<channel>/brief/{brief.md,examples/,images/}` + optional `events.json`; creative history shared by the channel's animations in `ai_data/channels/<channel>/creative/`. Settings: global in `config/ai.json` (models, effort/max_tokens per task, prices, budgets, limits, sandbox), per animation in its `ai` section (`channel`, `profile`, `video`, `max_bodies`, `sound`, `stock_target`, `events`, `publish_overrides`). `app/render_lock.py` is a cross-process lock: the scheduler takes it non-blocking, the studio blocking. AI scenes must call `anim_watch_world()` (`runtime/anim_box2d.h`): the runtime then reports bodies / off-screen / lost / NaN / moving fraction per tenth of the video in `metrics.json`, used to reject broken or frozen simulations.

### Logging
`setup_logging()` replaces `sys.stdout` with a tee that timestamps every `print()` into `logs/automation.log`. Use `print` for logging; there is no `logging` module setup.
